## 3. Sécurité — 19 / 100

### Ce qui est mesuré aujourd'hui

| Indicateur                                           | 30/07     | **11/09**     |
| ---------------------------------------------------- | --------- | ------------- |
| Routes API sans aucun contrôle d'accès               | 86 / 151  | **90 / 152**  |
| Fonctions `SECURITY DEFINER` exécutables par `anon`  | 315       | **332**       |
| `reset_finance_auto_data` exécutable par `anon`      | oui       | **oui**       |
| Policies RLS appelant la fonction de rôle sans cache | 216 / 334 | **216 / 334** |
| Tables sans policy RLS                               | 0 / 133   | **0 / 133**   |
| `middleware.ts` en production                        | absent    | **absent**    |

Le nombre de routes ouvertes **a augmenté de quatre**. Chaque nouvelle route écrite depuis
juillet part sans garde, parce qu'il n'existe aucune barrière centrale qui l'y oblige. C'est
le mécanisme, pas la négligence : `src/app/api` est un frère de `src/app/(protected)`, donc le
layout qui vérifie le rôle ne s'y applique jamais, et chaque route doit se protéger elle-même.

### Le point le plus grave, toujours ouvert

```
reset_finance_auto_data   exécutable par anon : oui
delete_organisation_safe  exécutable par anon : oui
mark_payment_received     exécutable par anon : oui
set_closed_fiscal_year    exécutable par anon : oui
invoke_edge_function      exécutable par anon : oui
get_linkme_users_emails   exécutable par anon : oui
```

`reset_finance_auto_data` fait un `DELETE FROM organisations` et désactive toutes tes règles
de rapprochement. La clé `anon` est publique : elle est dans le bundle JavaScript de LinkMe et
du site internet, lisible par n'importe qui avec un navigateur. Six semaines plus tard, c'est
toujours vrai.

Le compteur de fonctions exposées est passé de 315 à 332 et ne redescendra jamais tout seul :
c'est le `GRANT` par défaut de Postgres sur toute nouvelle fonction. Tant qu'aucune migration
ne se termine par un `REVOKE`, chaque fonction ajoutée creuse le trou.

### Ce qui est bien fait, et qu'il ne faut pas casser

La RLS est activée sur les 133 tables sur 133, et aucune table n'est sans policy. La
discipline existe — c'est son réglage qui est faux, pas son principe.

Et le code écrit en septembre est meilleur que celui de juillet :
`api/canaux/want-it-now/flux/route.ts` vérifie un `Authorization: Bearer`, répond 401 sans
jeton, et utilise une comparaison à temps constant. C'est exactement le motif qui manque aux
90 autres routes. `BO-SEC-002` a aussi retiré du suivi git un CSV de liste clients.

## 4. Performance — 22 / 100

### La mesure qui explique tout

| Table               | Lignes | Scans séquentiels | Tuples lus    |
| ------------------- | ------ | ----------------- | ------------- |
| `user_app_roles`    | **9**  | **262 390 637**   | 1 361 783 830 |
| `sales_orders`      | 190    | 1 011 815         | 146 273 188   |
| `bank_transactions` | 737    | 118 588           | 75 697 845    |
| `products`          | 236    | 1 554 502         | 54 735 819    |
| `organisations`     | 223    | 297 374           | 33 761 414    |

Regarde la colonne « Lignes ». **Ton application n'est pas lente à cause du volume de
données.** Tu as 236 produits, 190 commandes, 737 transactions, 223 organisations. C'est
minuscule. Une base correctement réglée répond à ça en une milliseconde.

Elle est lente parce que `is_backoffice_user()` est appelée sans mise en cache dans 216
policies RLS : Postgres la réévalue **une fois par ligne examinée**, et chaque évaluation
balaie entièrement la table des rôles. Afficher une liste de 236 produits déclenche 236
balayages complets d'une table de 9 lignes.

Depuis le 31 juillet, le compteur a pris **5,5 millions de scans supplémentaires** — environ
130 000 par jour d'usage normal.

### Le piège à ne pas retomber dedans

La recette évidente — envelopper l'appel en `(SELECT is_backoffice_user())` — a déjà été
appliquée le 2026-05-07 sur 64 policies. Le 2026-05-08 à 03:00, `SELECT FROM auth.users` est
passé à 3 955 ms, le service d'authentification a renvoyé 504 sur tous les jetons, et le
back-office est devenu inaccessible. Rollback le jour même
(`20260508060000_rollback_bo_rls_perf_002_003.sql`). **Ne pas la retenter.**

La solution qui tient : mettre le rôle dans le jeton de session. Un trigger sur
`user_app_roles` écrit un drapeau dans `raw_app_meta_data`, puis `is_backoffice_user()` est
réécrite en lecture pure du jeton, sans aucune entrée-sortie. La signature de la fonction ne
change pas, donc **aucune des 216 policies n'est modifiée** — c'est précisément ce qui avait
explosé en mai.

### Les autres maillons, tous inchangés

| Indicateur                                     | Valeur                                               |
| ---------------------------------------------- | ---------------------------------------------------- |
| `force-dynamic` sur les layouts                | **2 sur 2** — aucune page n'est jamais mise en cache |
| Boucles faisant une requête par ligne affichée | **25**                                               |
| Clés étrangères sans index couvrant            | **27**                                               |
| Packages déclarant `sideEffects: false`        | **0 sur 26**                                         |
| `optimizePackageImports` configuré             | **non**                                              |
| Fichiers de plus de 500 lignes                 | **73**                                               |

`force-dynamic` sur le layout racine interdit à Next.js de mettre quoi que ce soit en cache,
sur toutes les pages, y compris les écrans de configuration qui ne changent jamais. C'est la
raison précise pour laquelle la configuration du site internet met des secondes à s'afficher.

## 5. Scalabilité — 26 / 100

C'est le seul axe qui a **baissé**, et il faut comprendre pourquoi.

### Les types de base de données se sont multipliés

Sept copies du fichier de types Supabase, contre quatre en juillet :

```
apps/site-internet/src/lib/supabase.ts
apps/back-office/src/types/supabase.ts
packages/@verone/types/src/supabase.ts
packages/@verone/utils/src/supabase.ts
packages/@verone/types/packages/@verone/types/src/supabase.ts      <- répertoire imbriqué
packages/@verone/types/apps/back-office/src/types/supabase.ts      <- répertoire imbriqué
```

Les deux derniers sont des accidents : un script de génération a recréé toute l'arborescence
_à l'intérieur_ du package `types`. Personne ne les lit, mais ils sont dans le dépôt, ils sont
indexés par l'éditeur, et le jour où quelqu'un corrige un type il a une chance sur sept de le
faire au bon endroit.

### Le schéma n'est pas reconstructible

Sur 771 migrations, **six tables cœur n'ont aucun `CREATE TABLE`** : `products`,
`organisations`, `sales_orders`, `stock_movements`, `contacts`, `purchase_orders`. Aucun
fichier de baseline n'est committé.

Concrètement : si ta base disparaît, tu ne peux pas la reconstruire depuis le dépôt. Et aucun
environnement de test n'est reproductible — c'est ce qui bloque toute la stratégie de test
depuis juillet.

### Le reste

| Indicateur                    | 30/07    | **11/09**             |
| ----------------------------- | -------- | --------------------- |
| Cycles mutuels entre packages | 13       | **13**                |
| Packages `@verone`            | 26       | **26**                |
| Dont un script `build`        | —        | **5**                 |
| Arbre produit dupliqué        | 66 vs 66 | **66 vs 67 fichiers** |
| Clés étrangères sans index    | —        | **27**                |

Les 13 cycles sont identiques à juillet : `common` — la couche basse — importe `finance`,
`orders`, `organisations` et `products`. Ces quatre paquets forment un bloc indivisible.

L'arbre produit est toujours dupliqué en deux répertoires de 66 et 67 fichiers, et le
catalogue renvoie vers le moins complet des deux.

### La bonne nouvelle

Tes volumes ne bougent presque pas : +10 commandes, +1 organisation, +12 mouvements de stock
en six semaines. Tu n'as **aucune pression de croissance**. La dette de scalabilité ne te
coûte rien aujourd'hui en performance — elle te coûte du temps à chaque modification, et elle
te coûterait très cher le jour d'un incident de base.

Autrement dit : cet axe est le moins urgent des trois. Ne le traite pas avant la sécurité et
la performance.

## 7. Une remarque de méthode

Le chantier n'a pas avancé en six semaines, et la cause n'est pas le manque de temps : c'est
que le travail de juillet est resté dans une branche jamais poussée, pendant que trois autres
branches partaient sur d'autres sujets. Le reflog montre huit changements de branche sur la
seule journée d'aujourd'hui.

Deux garde-fous simples, sans outillage :

**Une branche se pousse le jour où elle est ouverte**, même incomplète, même en brouillon. Un
travail qui vit uniquement sur ton disque n'existe pas — il a failli être perdu deux fois
déjà.

**Un lot va jusqu'à la production avant qu'un autre commence.** Le Lot 005 est ouvert depuis
six semaines. Tant qu'il n'est pas déployé, les quatre routes API ajoutées entre-temps
creusent le trou qu'il était censé boucher.
